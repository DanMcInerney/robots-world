# Jev camera search and metric following: research recommendation

19 September 2026. Research and design synthesis only; no new inference, installation, simulation campaign or physical flight was run.

For the requirement that Jev chooses how the drone moves, I recommend calibrated RGB stereo, a persistent scene estimate with uncertainty, and Jev choosing complete short flight maneuvers from their predicted consequences. Acquisition, estimation, motion execution and emergency stopping continue locally while Jev evaluates a decision. This is a proposed design to test, not a qualified solution.

The missing experiment is the complete camera-derived metric search-and-follow integration. Compact maps and joint consequence menus are existing ideas; joint controls and multi-axis forecasts were already tested under other sensor assumptions. The strongest recent camera-derived component remains computed yaw consequences: framing improved from 29% to 74% in sixteen 20-second yaw trials. That result does not establish translation, metric following or recovery. The earlier full-mission confirmation remained 0/24. See the [handoff](JEV-CAMERA-FOLLOW-HANDOFF.md), [refinement results](jev-spatial-refinement-results.md), [reactive results](reactive-results.md) and [prior spatial proposal](jev-spatial-awareness-research.md).

## What I would build

1. **Persistent factual state.** Keep the selected target's original appearance, candidate identity associations, measured position and velocity, observation age and uncertainty. Keep a bounded local 3D map distinguishing observed free, occupied and unknown space, plus inspected viewpoints and briefly observed detection events. Separate moving objects from static geometry. During loss, retain plausible predicted locations with increasing uncertainty and their last observation time. A tracker ID alone does not establish that a newly seen car is the original car. Keep Jev's chosen intention and recent actual command receipts; treat the intention as a decision, not sensor truth.
2. **A small, explicit movement menu.** Start by testing perhaps 15–40 complete maneuvers that combine translation and yaw, including braking and observation-only rotations. This count is a proposal, not a proven optimum. Compute physical consequences for every option: range and bearing intervals, observed clearance, exposure to unknown space, and visibility hypotheses. Include camera mounting and flight attitude: pitching the drone changes a fixed camera's view. Jev chooses the maneuver and search/viewpoint decision; code does not supply a mission-weighted ranking in this arm.
3. **Predictions that cover execution.** Account for source age, inference/dispatch delay, the entire executable lease and braking. Evaluate swept 3D clearance, not just endpoint clearance. The earlier reactive campaign already exposed a 1.5-second preview followed by a three-second execution that violated the altitude floor. Execute only a bounded prefix, refresh observations, reject stale answers and preserve local Stop/goal-change authority. Safety vetoes are explicit, shared between comparison arms and logged. Unknown clearance must not become a guarantee.

Jev's official API allows [255 options per Choice](https://docs.typesafe.ai/primitives/choice). Questions in a batch [see the same state independently](https://docs.typesafe.ai/concepts/state), so one question cannot consume another question's target or mode answer. Complete target/maneuver options or explicitly conditional branches avoid that dependency. The [documented arithmetic limitations](https://docs.typesafe.ai/model-jaggedness/jev-1.13) support keeping transforms, elapsed time and predictions in code.

## Library choices

| Role | Recommendation and boundary |
| --- | --- |
| Integrated stereo, ego-motion and short object tracks | **[ZED SDK](https://docs.stereolabs.com/docs/development/zed-sdk/modules/object-detection/custom-object-detection)** is my practical baseline. It accepts custom detections and supplies metric 3D object estimates using depth and positional tracking. A ZED RGB stereo pair fits the two-camera limit. [ZED X](https://www.stereolabs.com/docs/products/cameras/zedx/specifications) has synchronized global shutters but requires Jetson and capture hardware; exact hardware depends on payload, power and measured range performance. [SDK requirements](https://docs.stereolabs.com/docs/development/zed-sdk/specifications). |
| Semantic recognition | **[YOLOE](https://docs.ultralytics.com/models/yoloe)** supports open-vocabulary categories and segmentation. For only a blue car, an ordinary vehicle detector plus colour/appearance evidence is a simpler starting point. Open vocabulary does not reliably resolve every contextual description or individual identity. |
| Strong learned-stereo challenger | **[Fast-FoundationStereo](https://github.com/NVlabs/Fast-FoundationStereo)**, CVPR 2026, is the substantive new comparison against SGBM. It uses calibrated, rectified stereo and provides TensorRT export. Published example latency uses an RTX 3090, so it establishes no onboard speed here. Research and commercial code/checkpoint terms differ. Treat it as a separate perception pipeline comparison, not an assumed drop-in replacement inside the closed ZED SDK. |
| Identity in a custom perception pipeline | **[BoT-SORT](https://github.com/NirAharon/BoT-SORT)** combines motion compensation and optional appearance Re-ID. Default supplied Re-ID work focuses on pedestrians; vehicle identity needs its own evidence. Start with one tracking owner: ZED tracking may make another tracker unnecessary. Preserve ambiguity through lookalike crossings and long occlusions. |
| Local geometry | **[nvblox C++](https://nvidia-isaac.github.io/nvblox/public/index.html)** is a candidate when a bounded 3D clearance map is needed. It consumes depth and pose; incorrect inputs remain incorrect geometry. Use explicit dynamic-object handling and bounds on mapped volume. Its ground-robot Nav2 examples are not a complete aerial planner. |
| MAVLink execution | **[MAVSDK Offboard with PX4](https://mavsdk.mavlink.io/main/en/cpp/guide/offboard.html)** supplies velocity/yaw control and automatic setpoint resending. Application-owned freshness leases must stop stale motion even if transport remains healthy. This is a PX4 recommendation; another autopilot needs its own control-mode contract. |

[Primitive-Planner](https://github.com/ZJU-FAST-Lab/Primitive-Planner) is a useful motion-library reference and [Elastic-Tracker](https://github.com/ZJU-FAST-Lab/Elastic-Tracker) a visibility-aware aerial-tracking reference. Their ROS research implementations are not drop-in Jev libraries. [acados](https://docs.acados.org/) becomes useful if constrained continuous optimization is required. A planner that selects pursuit trajectories performs policy work: label that system Jev-supervised rather than attributing those movement decisions to Jev.

## One camera and practical limits

For one camera, benchmark [Depth Anything 3 Metric](https://github.com/ByteDance-Seed/Depth-Anything-3), alongside the still-unexecuted Depth Anything V2 metric baseline. DA3's metric checkpoint requires the documented focal-length conversion; ordinary relative-depth checkpoints cannot be relabeled metres. Even an output expressed in metres requires validation around 10 m and through viewpoint changes. Stereo remains my preferred starting point for an explicit metric-distance objective.

Gemini's hierarchy is reasonable for Jev as a mission supervisor, but its search sweeps and tracking PID own decisions the user previously wanted Jev to make. It also overstates identity persistence and monocular scale reliability. A separate Jev judgment over a detector's text does not provide independent visual verification. Fixed altitude must agree with the distance definition: 15 m vertical separation makes 10 m line-of-sight separation impossible.

Two stereo cameras need overlapping views, so blind rear/lateral travel remains a limitation. Turn to inspect, retain recently observed free space with aging, and restrict motion when coverage is inadequate. Learned depth does not certify thin-wire avoidance. Standard [OAK-D](https://docs.luxonis.com/hardware/products/OAK-D) has three physical cameras, while the two-camera [OAK-D SR](https://docs.luxonis.com/hardware/products/OAK-D%20SR) is designed for short range; neither is an obvious substitute under this strict sensor budget.

## The next decisive experiment

First qualify target range around 10 m on matched recorded imagery, including real measurements, a moving camera, lookalikes and the old thin-obstacle regressions. Measure range error, foreground/background contamination, valid coverage and acquisition-to-decision age. Qualify obstacle clearance separately from target range.

Then run paired closed-loop simulation with identical initial conditions, exogenous target trajectories, perception code, candidate menu and safety layer. Images must depend on each controller's actual motion; fixed recordings cannot measure control outcomes. Compare Jev with a deterministic selector over the same candidates. Predeclare the comparator's search/coverage objective when no target is visible, and range/visibility objectives when following. A continuous MPC system can be an additional comparator, but changes in action space must be disclosed.

Advance from visible-target following to initially hidden search, similar-car crossings and occlusion requiring a new viewpoint. Score identity switches, time in a declared 10 m tolerance band, active reacquisition, collision/clearance, observation age, control interruptions and sustained duration separately. Inspect first divergences; aggregate failure alone does not locate its cause. No finite trial establishes indefinite reliability.
