# Choosing a simulator for the next testbed

Research date: 21 September 2026. Six parallel web-research lanes (MuJoCo, NVIDIA, Gazebo/Webots/CoppeliaSim, alternatives, natural-language robot design, independent comparisons) plus two local smoke tests on the development machine. Claims below are from primary pages the researchers fetched unless marked *inferred*; **measured** means it ran on this machine. The shared web-search budget ran out late in the session, so Reddit sentiment, McMaster-Carr API status and Chrono::Sensor details are unverified.

## Question

Which open-source library best supports (1) the present experiments — slow model controllers steering drones, rovers and arms through cameras, rangefinders and stereo while the world keeps moving — and (2) the larger goal: Claude Code turns "a 1 m arm, two joints, pressure-sensing fingertips, about $500" into a costed bill of materials and a simulated robot built from simplified real components?

## Recommendation

**Add MuJoCo as a physics backend and make MJCF (emitted through `MjSpec`) the generated-robot format.** Keep the six contracts, `SensorBank`, radio, MAVLink facade and recorder. Nothing outside the original shortlist is a better production-ready fit. Remove CoppeliaSim from the shortlist: its Edu licence forbids company, non-profit and research-institute use.

This is an adapter, not a rewrite. `PhysicsBackend.step` already permits a promise, and the core stays engine-neutral.

| Need | Why MuJoCo |
| --- | --- |
| World continues while a controller thinks | `mj_step` is called from our loop. No lockstep RL harness, no ROS. |
| TypeScript host on Windows 11 | **Measured:** DeepMind's official `@mujoco/mujoco` 3.13.0 loads in Node 24.15 in 48 ms, compiles the generated arm in 27 ms and steps at ~94,000 steps/s (~190× real time) in-process. Exposes `MjSpec`, `mj_ray`, `mj_multiRay`. Upstream calls these bindings work-in-progress. |
| Model generated by an agent | **Measured:** `MjSpec` build + compile of arm, sensors, camera and scene took 1.7 ms. Compile errors name the element and the parameter. MJCF is the format recent agentic robot-design work targets (SR-Platform, RobotDesignGPT, a published Claude Code MuJoCo scene skill). |
| Simplified realistic actuators | `gear`, `armature` (reflected rotor inertia), `forcerange`, `frictionloss`, damping and affine gain/bias come straight from datasheet numbers. [BAM](https://github.com/Rhoban/bam) (Apache-2.0) supplies identified friction models for the Feetech STS3215 and several Dynamixels in MuJoCo. |
| Pressure fingertips | `touch` sensors and the `touch_grid` taxel plugin. **Measured:** the plugin ships in the Windows wheel; a 4×4 pad localised an off-centre bump to one taxel reading the pad's full 1.96 N weight. |
| Camera pixels | **Measured:** headless 320×180 RGB in 4.7 ms and depth in 1.6 ms through Python `mujoco.Renderer`, with textures, lights, shadows and meshes. The present software rasteriser draws flat-coloured boxes only. |
| Repeatability | **Measured:** identical inputs gave bit-identical `qpos`. |
| Weight and health | `pip install mujoco` took 4.4 s; the whole venv is 132 MB. Apache-2.0, Google DeepMind, releases roughly monthly through 3.13.0 (9 Sept 2026), ~3.7 M PyPI downloads a month. |

## Why not the others

- **Isaac Sim 6.1 / Isaac Lab 3.0.** Code is now Apache-2.0/BSD-3, but Omniverse Kit, RTX and PhysX binaries carry a separate NVIDIA licence. Best sensors (RTX camera and lidar, TacSL tactile) and actuator models. Against it: 25–50 GB, cold starts of minutes, breaking renames at most major versions, documented non-reproducibility of camera tasks under a fixed seed ([IsaacLab #3505](https://github.com/isaac-sim/IsaacLab/issues/3505)), and an unresolved crash report on this exact GPU class ([IsaacLab #4961](https://github.com/isaac-sim/IsaacLab/issues/4961), RTX 5090 Laptop; driver downgrade is the reported workaround). Its repository does ship agent skills for building and validating USD articulations. Revisit only if photoreal perception becomes the bottleneck.
- **Gazebo Jetty.** Healthiest governance (OSRA) and the PX4-official simulator, so it is the route to autopilot-in-the-loop. Its own documentation calls Windows support experimental, which makes WSL2 the practical host here; grasp contact remains a long-standing complaint. Keep as a future external adapter, not the core.
- **Webots.** Best explicit lockstep/real-time switch and the most declarative sensor-noise fields (`DistanceSensor` lookup tables, `TouchSensor` force modes). No numbered release since R2025a (19 months), a single ODE-derived engine, runtime PROTO imports must be pre-declared, and it is nearly absent from current research and agentic-design work.
- **CoppeliaSim.** GPL core, but the usable distribution is Edu (academia only) or paid Pro/Lite. Not the open-source foundation this project wants.
- **Newton 1.6.** Apache-2.0 under the Linux Foundation (NVIDIA, Google DeepMind, Disney), Windows listed, MuJoCo-Warp inside. First 1.0 was April 2026 and minors still land monthly; Python and CUDA only; no sensor or rendering stack of its own. Watch it. MJCF is its import format, so choosing MuJoCo keeps this door open.
- **Genesis 1.x.** Widest sensor list, including tactile pads with hysteresis, crosstalk and dead taxels. Headline speed claims were shown to rest on degenerate settings ([issue #181](https://github.com/Genesis-Embodied-AI/genesis-world/issues/181)) and the Nyx renderer was still a closed wheel in mid-2026. Useful as an offline cross-check, not a foundation.
- **Drake.** The best-designed control loop surveyed (`AdvanceTo` with a target real-time rate) and hydroelastic contact, but no Windows support. Useful as a feasibility library inside WSL.
- **Project Chrono 10.** BSD-3, Windows first-class, strongest vehicles and deformable terrain. Consider only if rover–terrain fidelity becomes the experiment.
- **PyBullet, Colosseum, Cosys-AirSim.** Stale, archived (July 2026) and frozen respectively. Project AirSim (MIT) is alive if Unreal-grade drone imagery is ever required.
- **Stay on Rapier.** One researcher preferred this because it needs no language bridge. The Node measurement above removes that advantage. Rapier has no robotics sensor stack, no actuator models, no model zoo and no presence in any comparison found. Keep `rapierFactory` and `kinematicFactory`; they keep the backend contract honest.

## What MuJoCo does not give us

- The sensor `noise` attribute no longer perturbs readings (**measured**: both pads read an identical 2.873 N with `noise` set). `SensorBank` already owns noise, latency, dropout and staleness, so nothing is lost.
- No lidar sensor type: build scans from `mj_multiRay`, as the present ray sensors already do.
- The WASM build has no OpenGL renderer under Node. Camera pixels need either a small Python render sidecar loading the same MJCF and receiving `qpos`/mocap state at the camera rate, or the existing Three.js path fed by `mjv_updateScene`. Rendering stays a pure function of recorded state, which suits principle 10.
- Two convention traps found while testing, both to be fixed once in the generator rather than left to a model: `MjSpec` and MJCF default to **degrees** (radian joint limits were silently read as ±0.2°), and `touch_grid` looks along the site's **−z** like a camera. A static base is welded to the world, so parent–child collision filtering does not apply to it.
- Some invalid `MjSpec` plugin configurations have crashed instead of raising ([#2757](https://github.com/google-deepmind/mujoco/issues/2757)); compile generated models in a disposable process. Meshes collide as convex hulls; decompose with CoACD.
- No maintained PX4 or ArduPilot bridge. The MAVLink facade is unaffected.
- Built-in rendering is clean rasterisation, not photorealism.

## Shape of the natural-language robot pipeline

Prior art (Text2Robot, RoboMorph, Articulate-Anything, Infinigen-Sim, Cadless) points to one pattern: the model writes a constrained program or parts graph, deterministic code emits the simulator format, and compile plus simulation feedback closes the loop.

1. **Parts database**: no open, priced, machine-readable catalogue of actuators and structure exists. Seed a small JSON set by hand from itemised open-hardware bills of materials — SO-ARM100/101 (follower arm $121.94; STS3215 servo $13.89), Koch v1.1, LeKiwi, Berkeley Humanoid Lite (~$188 per actuator). Octopart/Nexar covers electronics pricing only.
2. **Design as a parts graph** in our own JSON: components, mounts, joints, sensors. Cost and mass are roll-ups.
3. **Deterministic emitter** to MJCF through `MjSpec`, owning units, frames, reflected inertia (`rotor inertia × ratio²`), torque limits and sensor sites. Repeated sub-assemblies use `MjSpec` attachment.
4. **Feasibility before simulation**: gravity torque at worst pose against stall torque (**measured** in the smoke test: 2.08 N·m demanded of a 3.4 N·m servo with the 0.97 m arm horizontal), reach through [mink](https://github.com/kevinzakka/mink), speed, payload, power.
5. **Geometry when primitives are not enough**: build123d or CadQuery in a sandbox, trimesh for mass properties, CoACD for collision hulls.
6. **Run the same controller tests** through the unchanged `RobotPort`.

## Proposed first step

A `mujocoFactory` behind the existing `PhysicsBackend` contract using `@mujoco/mujoco`, passing the present backend tests, with primitive `RobotAsset` translated to MJCF. Then one paired Jev camera-follow run on Rapier and on MuJoCo to confirm the controller-facing behaviour is unchanged before any asset work. None of this is implemented or tested yet; the smoke tests in [experiments/simulator-eval](../experiments/simulator-eval/README.md) show only that the pieces run on this machine.
